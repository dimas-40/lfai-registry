# 공동인증서 PC→모바일 이전 — 다음 주 수요일 동석 작업 준비

> 박씨 지시(2026-09-18): "이거 챌린징으로 해 가지고 다음 주 수요일 날 나랑 같이 작업해야 돼."
> 전자소송 앱(`go.scourt.mcs`)·인터넷등기소 앱(`kr.go.iros`)에서 ADB 자동화 테스트를 하려면
> PC에 있는 공동인증서를 폰에 등록해야 함. Claude 사전 리서치 결과.

## 표준 절차 — QR 복사

거의 모든 은행/공공기관이 "KeySharpNX"라는 공통 중계 모듈(이니텍 계열)로 QR 복사를 표준
지원함(하나은행/KB/우리은행/서울시ETAX/다올저축은행 등에서 동일 패턴 확인):

1. **PC**: 사이트 인증센터 → 스마트폰 인증서 복사 → 인증서 내보내기(QR코드) → 인증서 선택
   → 비밀번호 입력 → QR코드 생성
2. **모바일 앱**: 메뉴 → 인증/보안 → 공동인증서 → "PC에서 인증서 가져오기" → QR코드 스캔

**같은 와이파이 불필요** — 로컬 통신이 아니라 인터넷 경유 중계서버(443포트)를 거침. 단, 특정
공유기/사내망 방화벽이 중계서버 접속을 막는 사례가 있어 실전에서는 "Wi-Fi 안 되면 LTE로
전환해서 재시도"가 표준 대응으로 언급됨 — 오히려 PC/폰이 각자 다른 네트워크(하나는 와이파이,
하나는 LTE)인 편이 더 안정적일 수 있음.

## 사이트별 확인 사항

| 사이트 | 확인된 것 | 확인 안 된 것 (수요일 직접 확인 필요) |
|---|---|---|
| 전자소송포털 (go.scourt.mcs) | 2026-02-17 차세대 개편으로 앱 전면 개편됨. 인증서 관련 메뉴 존재(추정) | **정확한 메뉴명, QR 스캔형인지 12자리 승인번호 입력형인지** — 공식 매뉴얼 원문 JS 렌더링이라 못 읽음, 앱 실행 후 직접 확인 |
| 인터넷등기소 (kr.go.iros) | PC 사이트: 우측상단 메뉴 → 기타 → 인증센터 → 인증서관리 → "PC-스마트폰 인증서 복사". 앱에도 동일 기능 + 모바일OTP 발급/재발급 병행. 2025-08부터 전자신청 시 OTP 필수 추가됨(인증서+OTP 이중체계로 이행 중) | 없음 — 절차 확인됨 |

## 금융인증서로 우회 가능한가 — 상충 정보, 미검증

전자소송포털은 로그인 자체는 금융인증서/PASS 등 복수 수단을 지원하는 것으로 보이나,
**"본인 명의 공동인증서 등록이 실제 이용의 전제조건"이라는 안내**와 **"PC/모바일 양쪽에서
금융인증서로도 전자서명 가능"이라는 상충되는 안내**가 둘 다 검색됨 — 어느 쪽이 맞는지
본문 직접 확인 못함.

**수요일 최우선 확인 사항**: 전자소송에서 실제 "전자서명 제출" 액션까지 금융인증서만으로
되는지. 만약 된다면 이 QR 복사 작업 자체가 통째로 불필요해질 수 있음 — 이걸 제일 먼저
테스트해볼 가치가 있음.

## 흔한 문제(Gotcha)

| 문제 | 원인 | 대응 |
|---|---|---|
| QR 무결성 검증 실패 | 승인번호/QR 유효시간 만료 | PC에서 QR 재생성 후 즉시 스캔 |
| 중계서버 접속 실패 | 방화벽이 443포트 차단 | 3G/LTE로 전환 재시도, 백신 방화벽 예외 등록 |
| KeySharpNX 손상 경고 | 인증서 복사 모듈(KSCertRelayMain.dll) 변조/손상 감지 | 모듈 삭제 후 재설치 |
| 인증서 만료 임박 | 유효기간 1년, 갱신 안 하면 복사돼도 로그인 불가 | 사전에 PC에서 유효기간 확인 — **수요일 전에 미리 체크 가능** |
| 보안모듈 충돌(이니세이프/델피노/안랩) | 벤더별 보안모듈이 QR 중계와 상호간섭 | 최신버전 재설치, 다른 보안모듈 임시 비활성화 |
| USB 수동복사 시 파일 미인식 | NPKI 폴더 구조 그대로 복사 안 하면 앱이 인증서 못 찾음 (QR 실패시 폴백 수단) | signCert.der+signPri.key를 NPKI 폴더 구조 그대로 폴더째 복사 |

## 수요일 세션 진행 순서 (제안)

1. **사전(박씨, 수요일 전)**: PC 인증서 유효기간 확인 — 만료 임박이면 갱신부터.
2. **당일 1단계**: 전자소송포털에서 "금융인증서만으로 전자서명까지 되는지" 먼저 테스트 —
   된다면 QR 복사 스킵, 안 되면 2단계로.
3. **당일 2단계**: 인터넷등기소부터 QR 복사 시도(절차 확정된 쪽이라 성공 가능성 높음) →
   성공 흐름 확인 후 전자소송에 동일 절차 적용.
4. **당일 3단계**: 두 앱 모두 인증서 등록 완료 후, 인증서/OTP 입력 화면에서 FLAG_SECURE
   여부 실측 ([`../../교재/FLAG_SECURE_동석경계_및_행정문해력_20260918.md`](../../교재/FLAG_SECURE_동석경계_및_행정문해력_20260918.md) 참조) — 이 순간은 **동석 필수**, 박씨가 직접 수행.

## 이 작업이 교재 자산으로 이어지는 지점

앱마다 다른 인증서 복사 UX(승인번호 입력형 vs QR형), 흔한 실패 원인, FLAG_SECURE 여부를
실측·기록하면 그대로 `교재/정부법률사이트_앱현황_검증_20260918.md`의 "앱있음/앱없음" 분기표
다음 단계인 **"인증서 등록 난이도 매트릭스"**로 이어져 교재 1장(한계선) 실증 자료가 됨.

## 부록: 공인인증서 제도의 역사·기술적 성격 — 왜 이렇게 됐는가 (2026-09-18)

수요일 작업 전 알아두면 좋은 배경. "왜 한국만 이렇게 복잡한가"에 대한 정확한 답.

### 미국 비교 — PACER/CM-ECF

미국 연방법원 전자소송 시스템(PACER/CM-ECF)은 별도 인증기관 발급 전자서명 인증서 개념
자체가 없음. 아이디+비밀번호, 일부는 2단계인증(OTP) 추가 정도. 변호사든 나홀로소송이든
동일 방식. 유럽도 나라마다 다르나 에스토니아처럼 강력한 전자ID가 있는 곳도 "산업
진입장벽"이 아니라 전 국민 신분증 자체의 디지털화라 성격이 다름.

### 한국 공인인증서 — 시간순으로 보면 "AI 방어"가 아니라 "카르텔 보호"였음

- 1999년 전자서명법으로 시작 — 이 시점엔 스마트폰도, LLM도 없었음. **AI 자동화를 막으려는
  의도는 시간순서상 성립 불가능.**
- 대신 실제로 있었던 것: 1999년부터 **딱 6개 지정기관**(한국정보인증 등)만 공인인증서
  발급 가능 → **21년간 독점**. 매년 갱신 수수료를 받는 구조가 법으로 보장됨.
- 2020년 "천송이 코트" 사건(한류 드라마 옷을 외국인이 액티브X 때문에 못 사는 문제가
  공론화)을 계기로 전자서명법 20년 만에 전면개정 → 공인인증서 독점 폐지. 지금 쓰는
  "**공동인증서**"라는 이름 자체가 그 개정의 결과물.
- **정확한 결론**: "AI 못 하게 병풍 세운 것"이 아니라, "1999년에 만든 낡은 독점구조가
  2020년에 뒤늦게 해체됐는데, 그 잔재(사이트마다 다른 보안모듈, 반복 인증서 로그인)가
  아직도 안 없어진 것". 산업 보호 효과는 진짜 있었지만 타겟은 AI가 아니라 신규
  발급기관 진입 차단(자기들끼리)이었음.

### 보안키패드(랜덤배열) — 막는 건 "좌표 재생"이지 "화면 읽기"가 아님

- 랜덤배열 키패드는 원래 **키로거**(키보드 입력 가로채기)나 **고정좌표 매크로**(항상 같은
  자리 클릭)를 막으려고 설계됨 — 2000년대 초반 위협모델.
- Claude in Chrome 같은 **비전 기반 에이전트는 매번 화면을 새로 보고 숫자 위치를 찾아서
  클릭**하기 때문에 배열이 매번 바뀌어도 상관없음 — 애초에 비전 AI라는 위협모델 자체가
  설계 당시 존재하지 않았음.
- **그렇다고 "동석 필수" 원칙이 무의미해지는 건 아님** — 동석이 필요한 이유는 "AI가
  기술적으로 못 뚫어서"가 아니라 **"서명은 되돌릴 수 없고 잘못되면 법적 책임이 발생하는
  지점이라 사람이 마지막에 확인해야 한다"**는 것. 오조작으로 다운로드 파일 219개를 날린
  사고([[project_ecourt_gui_automation_prep]])와 같은 구조 — 기술적으로 클릭할 수 있다는
  것과 클릭해도 되냐는 것은 완전히 다른 질문.
- **미확인 리스크**: 많은 보안모듈이 랜덤키패드만으로 안 끝내고 **마우스 이동 패턴·클릭
  타이밍**까지 봐서 봇 여부를 판별함(사람=곡선+불규칙 간격, 스크립트=직선 순간이동+규칙적
  간격). 걸리면 세션 차단·계정 잠금까지 갈 수 있음 — **수요일 실전 전 이 모듈이 그런
  탐지를 하는지 확인 필요**. 안드로이드 ADB의 터치 이벤트(`input tap` 좌표점프)도 똑같은
  탐지 대상이 될 수 있음 — PC와 모바일 양쪽에서 동일 여부 확인.

### 모바일 전환이 안 된 영역의 패턴 — "쓰는 사람이 적어서" 후순위로 밀림

- 정부24/홈택스(손택스)/고용24 = 전환 완료(앱 네이티브). 전자소송/인터넷등기소/특허로 =
  전환 안 됨(PC/웹 중심). 갈림 기준은 **"사용빈도 × 금전적 리스크"**.
- 홈택스는 전 국민이 매년 써서 앱 투자 회수가 되고 국민 편의성 압박도 큼. 전자소송은
  평생 한두 번, 잘못되면(오접수·서명오류) 법적 효력이 걸리는 고위험 행위 — 정부 입장에서
  모바일 최적화 투자 유인이 낮음. **기술이 안 되는 게 아니라 예산 우선순위에서 밀린 것.**
- 정확한 표현: "핸드폰 트랜지션이 안 됐다"가 아니라 **"저빈도·고위험 영역이 저빈도이기
  때문에 후순위로 밀렸다"** — 사용자 수가 안 느니까 예산도 안 붙는 구조적 정체. 시간이
  지난다고 자연 해결되는 문제가 아님.

### 추론 — 이게 buckleychang에 의미하는 것

세 가지(카르텔 잔재, 위협모델 구식화, 저빈도 후순위)의 공통점은 **전부 "AI를 막으려는
설계"가 아니라 "다른 이유로 생긴 낡은 구조가 방치된 것"**이라는 점이다. 이 재해석이
buckleychang 포지셔닝을 바꾼다:

- **바뀌기 전 프레이밍**: "AI로 보안을 우회해서 자동화한다" — 방어적으로 들리고, 자동화
  탐지에 걸리면 계정 잠금 등 실제 리스크도 있음.
- **바뀐 후 프레이밍**: "정부가 예산을 안 줘서 20년 넘게 방치한, 저빈도·고위험 사용자
  집단(나홀로소송 하는 사람들)을 위한 다리를 민간이 대신 놓는다" — 이건 보안 우회가
  아니라 **정부가 안 채운 서비스 갭을 메우는 것**. 오늘 ADB로 이미 뚫어놓은 그 다리 자체가
  "정부가 안 해준 모바일 전환을 개인이 자기 손으로 해낸 것"이라는 콘텐츠 가치를 가짐.
- 단, 이 프레이밍 전환이 **봇 탐지 리스크 자체를 없애주진 않음** — 실제 소송 계정이 잠기면
  진행 중인 사건에 실질적 타격이 있으므로, 수요일 테스트는 반드시 탐지 여부를 먼저 낮은
  강도로 확인하고 진행할 것 (계정 잠금은 취소 불가능한 종류의 사고 — [[feedback_no_blind_kill_claude]]류 "되돌릴 수 없는 조작은 신중히"와 같은 원칙 적용).
